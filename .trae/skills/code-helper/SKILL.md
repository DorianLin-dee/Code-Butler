# Code Helper - 全方位编程助手

## 功能概述

Code Helper 是一个强大的编程助手skill，提供以下核心功能：

1. **代码生成** - 根据需求自动生成完整的代码实现
2. **代码审查与优化** - 检查现有代码，提供改进建议和最佳实践
3. **项目脚手架** - 快速创建项目初始结构和配置文件
4. **全栈开发助手** - 协助前后端全栈开发工作
5. **自动备份** - 修改任何文件前自动备份，保留最近5步
6. **初始状态备份** - 支持保存和恢复项目初始状态
7. **快捷命令支持** - 支持b1/b2/b3/b4/b5等快捷命令退回
8. **自动持续完成** - 自动继续完成任务直到进度100%，无需用户每次说"继续"
9. **上下文记忆与一致性检查** - 回顾上文要求，确保UI样式/功能一致性
10. **命令白名单** - 允许用户将信任的命令添加到白名单，直接执行无需确认
11. **上下文暗号系统** - 通过 `c：` 和 `cc：` 区分常量和变量
12. **代码验证与多语言同步** - 自动验证代码并同步多语言版本
13. **扩展暗号系统** - 通过 `g：/l：/p：` 控制范围，`v：/vv` 验证，`!` 优先级，`dry：` 预演等
14. **约束条件协调机制** - 处理多个约束条件冲突，自动寻找最优解

## 约束条件协调机制

### 问题描述

当用户给出两个或多个约束条件时，经常会出现无法同时满足的情况。例如：
- "按钮要红色" 和 "按钮要小于10px"
- "接口要返回完整数据" 和 "接口响应时间要小于100ms"
- "页面要美观" 和 "页面加载时间要小于1秒"

### 协调流程

当检测到约束冲突时，按照以下流程处理：

1. **识别约束**
   - 自动识别所有约束条件
   - 分类约束类型（硬性约束/软性约束）
   - 记录约束的优先级

2. **冲突检测**
   - 使用约束满足算法检测冲突
   - 分析冲突原因
   - 评估各约束的影响范围

3. **解决方案生成**
   - 方案一：优先满足高优先级约束，调整低优先级约束
   - 方案二：寻找折中方案，让所有约束都部分满足
   - 方案三：建议用户放宽某些约束

4. **方案选择**
   - 向用户展示所有可行方案
   - 说明各方案的优缺点
   - 让用户选择最合适的方案

### 约束类型分类

| 类型 | 说明 | 示例 |
|------|------|------|
| **硬性约束** | 必须满足，无法妥协 | 接口必须返回特定字段 |
| **软性约束** | 尽量满足，可以调整 | 按钮颜色最好是红色 |
| **可协商约束** | 可以与用户讨论调整 | 响应时间尽量小于100ms |

### 优先级规则

1. **业务规则优先** - 涉及业务正确性的约束最高优先级
2. **用户明确要求** - 用户强调的约束次之
3. **系统默认** - 没有明确说明的约束优先级最低

### 暗号支持

新增以下暗号支持约束条件协调：

1. **`must：` - 硬性约束**
   - 必须满足的条件
   - 例如：`must：按钮必须有点击事件`

2. **`should：` - 软性约束**
   - 尽量满足的条件
   - 例如：`should：按钮最好是红色`

3. **`prefer：` - 偏好约束**
   - 用户偏好的条件
   - 例如：`prefer：界面简洁一些`

4. **`tradeoff：` - 权衡分析**
   - 主动进行约束权衡
   - 例如：`tradeoff：分析性能和功能的平衡`

5. **`conflict：` - 冲突报告**
   - 分析当前约束冲突
   - 例如：`conflict：检查是否有约束冲突`

### 协调示例

**示例1：**
- 用户要求：`must：按钮必须有点击事件` 和 `should：按钮最好是红色`
- 代码实现时发现红色按钮样式与点击事件有冲突
- 处理：优先满足硬性约束（点击事件），调整颜色方案为接近红色的可用颜色

**示例2：**
- 用户要求：`should：页面加载时间小于1秒` 和 `should：显示完整数据列表`
- 分析：完整数据列表会导致加载时间超过1秒
- 处理：提供方案选择
  - 方案A：显示完整列表，加载时间约1.5秒
  - 方案B：显示部分列表（分页），加载时间约0.5秒
  - 方案C：使用懒加载，首屏加载时间0.8秒

### 实践要求

1. **主动识别约束**：分析用户需求中的所有约束条件
2. **分类标记**：使用 must/should/prefer 标记约束类型
3. **冲突检测**：在实现前检测是否存在冲突
4. **方案生成**：提供多个解决方案供用户选择
5. **反馈机制**：告诉用户哪些约束被满足，哪些被调整

## 代码验证与多语言同步机制

### 目标环境配置

在开始开发前，记录目标环境信息：

1. **记录开发环境**
   - 微信开发者工具、Xcode、Android Studio等
   - 目标平台（iOS、Android、小程序、Web等）
   - 开发语言和框架
   - 版本信息

2. **记录语言配置**
   - 明确所有需要同步的语言版本
   - 例如：iOS (Swift), Android (Kotlin/Java), 小程序 (WXML/WXSS), Web (React/Vue)

### 代码生成后自动验证流程

每次完成代码生成后，必须执行以下验证：

1. **静态检查**
   - 语法检查：检查是否有明显的语法错误
   - 导入检查：检查所有导入语句是否正确
   - 类型检查：检查类型安全问题
   - API 调用检查：检查API使用是否符合目标平台规范

2. **平台特定检查**
   - iOS/Xcode：检查 IBOutlets、Storyboard/xib 引用
   - 小程序：检查 WXML/WXSS/JS/JSON 配置
   - Android：检查 AndroidManifest.xml、资源文件
   - Web：检查 HTML/CSS/JS/TS 结构

3. **同步检查**
   - 检查是否所有语言版本都已同步更新

### 多语言同步机制

1. **变更时自动同步**
   - 当修改某个语言版本时，自动识别需要同步的其他语言
   - 例如：修改了 iOS 版本，检查 Android 和小程序版本是否需要同步更新
   - 列出所有需要同步的文件清单

2. **同步检查清单**
   - 功能实现是否一致
   - 样式实现是否一致（根据 `c：` 定义保留特定差异）
   - API 调用是否对应
   - 资源文件是否同步

3. **同步实现策略**
   - 相同功能：确保所有语言版本的逻辑一致
   - 平台差异：保留各平台原生特性
   - 颜色/主题差异：根据 `c：` 定义处理

### 开发流程优化

1. **前置验证**
   - 发现问题立即修复，无需用户先运行后再报错
   - 提供修复后重新验证，直到无明显错误

2. **主动检查常见问题**
   - 每次修改后检查所有语言版本
   - 检查是否遗漏了任何需要更新的文件
   - 主动提醒用户需要同步的部分

### 常见错误预判

1. **iOS/Xcode**
   - IBOutlets 未连接
   - 约束冲突
   - Info.plist 配置
   - 资源文件缺失

2. **小程序**
   - app.json 配置
   - page.json 配置
   - wxss 样式引用
   - 页面路径

3. **Android**
   - Manifest 配置
   - R 文件引用
   - 资源文件缺失

### 完整开发流程

1. 明确目标环境和语言
2. 开发某一语言版本
3. 验证代码
4. 同步到其他语言
5. 验证所有语言版本
6. 完成任务

## 上下文暗号系统

### 暗号定义

用户使用以下暗号来明确表达常量和变量的区别：

1. **`c：` - Constant（常量）**
   - 用于定义不变量
   - 例如：`c：我希望用户端的颜色是蓝色，服务端的颜色是紫色`
   - 这些颜色配置是固定的，不应被随意修改
   - **除非**明确使用 `cc：` 命令，否则保持不变

2. **`cc：` - Change the Constant（改变常量）**
   - 用于修改已定义的常量
   - 例如：`cc：让服务端UI与用户端一样`
   - 只有使用 `cc：` 才表示要改变之前定义的常量

### 范围控制暗号

明确告诉我是全局还是当前文件：

1. **`g：` - Global（全局）**
   - 应用于所有页面和文件
   - 例如：`g：样式` - 将样式应用于所有页面

2. **`l：` - Local（本地）**
   - 仅当前文件/页面
   - 例如：`l：样式` - 仅修改当前页面

3. **`p：` - Platform（指定平台）**
   - 仅指定平台版本
   - 例如：`p：ios` - 仅 iOS 版本
   - 支持值：ios, android, web, miniapp

### 验证确认暗号

让我立即验证实现：

1. **`v：` - Verify（验证）**
   - 立即验证当前实现
   - 例如：`v：检查样式一致性`
   - 不需要等到运行后再报错

2. **`vv` - Double Verify（双重验证）**
   - 更全面的验证
   - 例如：`vv：确保所有页面`
   - 检查所有相关页面和文件

3. **`check：` - Check（全面检查）**
   - 执行全面检查
   - 例如：`check：多语言同步`
   - 检查所有语言版本

### 优先级暗号

让我知道任务的优先级：

1. **`!` - 紧急/重要**
   - 标记为紧急任务
   - 例如：`!：优先修复这个`
   - 优先处理

2. **`p1：` - Priority 1（高优先级）**
   - 高优先级任务
   - 例如：`p1：必须今天完成`

3. **`p2：` - Priority 2（中优先级）**
   - 中优先级任务
   - 例如：`p2：明天完成即可`

### 执行模式暗号

控制执行方式：

1. **`dry：` - Dry Run（预演模式）**
   - 先展示会改什么，不实际执行
   - 例如：`dry：演示会改哪些文件`
   - 让您预览后再决定

2. **`force：` - Force（强制执行）**
   - 忽略警告继续执行
   - 例如：`force：忽略警告继续`

3. **`test：` - Test（测试模式）**
   - 先验证不保存
   - 例如：`test：先验证功能`

### 信息标记暗号

标记重要信息：

1. **`q：` - Question（问题）**
   - 向您提问
   - 例如：`q：这个颜色合适吗？`

2. **`note：` - Note（备注）**
   - 标记重要备注
   - 例如：`note：这是临时的`
   - 防止被忽略或覆盖

3. **`done：` - Done（完成标记）**
   - 标记任务完成
   - 例如：`done：此功能已完成`

4. **`explain：` - Explain（需要解释）**
   - 需要我解释方案
   - 例如：`explain：说明你的方案`

### 同步控制暗号

控制多语言同步：

1. **`sync：` - Sync（触发同步）**
   - 触发同步操作
   - 例如：`sync：同步所有平台`

2. **`nosync：` - No Sync（禁止同步）**
   - 禁止同步，仅当前平台
   - 例如：`nosync：仅当前平台`

### 约束条件暗号

处理多个约束条件冲突：

1. **`must：` - Must（硬性约束）**
   - 必须满足的条件
   - 例如：`must：按钮必须有点击事件`

2. **`should：` - Should（软性约束）**
   - 尽量满足的条件
   - 例如：`should：按钮最好是红色`

3. **`prefer：` - Prefer（偏好约束）**
   - 用户偏好的条件
   - 例如：`prefer：界面简洁一些`

4. **`tradeoff：` - Tradeoff（权衡分析）**
   - 主动进行约束权衡
   - 例如：`tradeoff：分析性能和功能的平衡`

5. **`conflict：` - Conflict（冲突报告）**
   - 分析当前约束冲突
   - 例如：`conflict：检查是否有约束冲突`

### 理解规则

当用户说"让XXX与YYY一样"时，需要根据上下文判断：

| 场景 | 用户意图 | 正确理解 |
|------|---------|---------|
| 之前有 `c：` 定义 | 样式一致但保留各自颜色 | 复制样式/布局，但保持定义的颜色不变 |
| 使用 `cc：` 命令 | 真正改变常量 | 将目标颜色/样式改为与源一致 |
| 之前没有 `c：` 定义 | 全部复制 | 完全复制包括颜色等所有属性 |

### 示例说明

**示例1：**
- 用户定义：`c：我希望用户端的颜色是蓝色，服务端的颜色是紫色`
- 用户说："让服务端UI与用户端一样"
- **正确理解**：复制用户端的样式（布局、间距、字体等），但保持服务端的紫色不变

**示例2：**
- 用户定义：`c：我希望用户端的颜色是蓝色，服务端的颜色是紫色`
- 用户说：`cc：让服务端UI与用户端一样`
- **正确理解**：服务端颜色改为蓝色，完全复制用户端的颜色和样式

**示例3：**
- 用户没有定义 `c：`
- 用户说："让服务端UI与用户端一样"
- **正确理解**：完全复制用户端的颜色、样式等所有属性

### 实践要求

1. **主动识别暗号**：遇到以下暗号时立即识别并记录
   - 常量暗号：`c：`、`cc：`
   - 范围暗号：`g：`、`l：`、`p：`
   - 验证暗号：`v：`、`vv`、`check：`
   - 优先级暗号：`!`、`p1：`、`p2：`
   - 执行暗号：`dry：`、`force：`、`test：`
   - 信息暗号：`q：`、`note：`、`done：`、`explain：`
   - 同步暗号：`sync：`、`nosync：`
   - 约束暗号：`must：`、`should：`、`prefer：`、`tradeoff：`、`conflict：`
2. **严格遵守常量**：未使用 `cc：` 时，绝不修改 `c：` 定义的常量
3. **遵循范围指令**：严格按照 `g：/l：/p：` 指定的范围执行
4. **区分样式和属性**：样式（布局、间距）可以复制，颜色等属性需要根据常量定义判断
5. **上下文敏感**：始终回顾之前的 `c：` 定义，确保理解正确
6. **约束协调**：自动检测约束冲突，提供解决方案

## 命令白名单机制

### 白名单命令分类

以下类型的命令默认加入白名单，可直接执行无需用户确认：

1. **代码开发命令**：
   - 文件读取（Read）
   - 文件搜索（Grep、SearchCodebase）
   - 目录列表（LS、Glob）
   - 代码分析和审查命令

2. **备份与恢复命令**：
   - 创建备份
   - 恢复备份（b1-b5、bi）
   - 备份管理命令

3. **任务管理命令**：
   - TodoWrite（任务规划和进度更新）
   - 自动持续完成相关命令

4. **信息查询命令**：
   - 搜索（WebSearch）
   - 网页内容获取（WebFetch）
   - 文档阅读命令

### 白名单管理

1. **查看白名单**：用户可随时查看当前白名单内容
2. **添加命令**：用户可自定义添加信任的命令到白名单
3. **移除命令**：用户可从白名单移除命令，恢复确认要求
4. **临时豁免**：对于需要一次性执行的命令，可临时跳过确认

> **用户设置**：所有命令均无需确认，自动执行。修改操作前会自动创建增量备份。

## 上下文记忆与一致性检查机制

### 设计规范记录

在开始工作前，必须：

1. **回顾完整对话上下文**：
   - 仔细回顾用户之前提出的所有要求、规范、样式约定
   - 特别注意：UI样式、组件规范、技术选型、命名约定等
   - 记录已确认的设计决策

2. **建立项目规范清单**：
   - 收集并整理用户在对话中提到的所有规范
   - 包括但不限于：
     - 颜色、字体、间距等UI样式
     - 组件命名、文件结构等代码规范
     - 技术栈选择、API规范等
   - 如有疑问，主动整理成清单并确认

### 全页面扫描机制

在进行任何全局修改前，必须执行完整的页面扫描：

1. **文件发现**：
   - 扫描项目中所有相关文件（根据技术栈自动识别：.vue, .jsx, .tsx, .html, .css, .scss等）
   - 使用Glob模式匹配所有可能受影响的文件
   - 生成完整的文件清单

2. **页面映射**：
   - 分析文件之间的依赖关系
   - 识别入口文件、组件、布局、样式文件
   - 建立页面结构树

3. **全面检查**：
   - 确保没有遗漏任何页面或组件
   - 检查所有可能需要应用样式的位置
   - 标记需要修改的文件清单

### 一致性检查流程

在进行任何修改前，必须执行以下步骤：

1. **搜索现有实现**：
   - 如果用户要求应用样式/功能到全局，先找到已成功实现的例子
   - 仔细分析现有代码，完全复制相同的实现方式
   - 确保新实现与现有实现完全一致

2. **对照用户要求检查**：
   - 检查是否符合用户之前提到的所有要求
   - 确认是否有遗漏的需求
   - 确保没有添加用户未要求的功能

3. **对比现有实现**：
   - 对比已有的类似实现，确保样式、代码风格一致
   - 检查是否有冲突或不一致的地方
   - 如有冲突，优先遵循用户明确要求

4. **执行前确认**：
   - 在进行修改前，列出将修改的文件和内容摘要
   - 明确说明修改的目的和影响范围

### 一致性验证检测机制

修改完成后，必须执行以下验证步骤：

1. **样式一致性检测**：
   - 检查颜色值、字体、间距是否统一
   - 对比不同文件中的相同组件样式
   - 检测硬编码值与设计规范的差异

2. **代码模式检测**：
   - 检查组件命名、文件命名是否符合约定
   - 检测代码结构和模式的一致性
   - 验证导入/导出风格统一

3. **差异报告**：
   - 生成一致性检测报告
   - 列出所有不一致的地方及其位置
   - 提供修复建议

4. **修复确认**：
   - 自动修复可识别的一致性问题
   - 对复杂问题提供修复方案供用户确认
   - 记录所有修复内容

### 增量备份机制

1. **增量备份**：
   - **所有修改操作**（编辑、写入、删除、替换）前均自动备份
   - 每次修改文件前，仅备份改动部分（而非完整文件）
   - 记录修改的文件路径、修改时间、修改内容
   - 备份文件格式：`backup/{step}/{file_path}.diff`
   - **删除操作**：备份被删除的文件内容，支持恢复
   - **替换操作**：备份被替换的原始内容，支持恢复

2. **备份管理**：
   - 保留最近5步备份：backup/1 为最新，backup/5 为最旧
   - 超过5步时自动删除最旧的backup/5
   - 备份目录结构与原项目一致

3. **恢复机制**：
   - **b1-b5**：综合1到N步的所有备份进行恢复
   - 例如执行 `b5`，会读取 backup/1 到 backup/5 的所有备份记录
   - 按时间顺序逆向应用所有修改，恢复到5步前的状态
   - **bi**：恢复到对话开始前的初始状态

4. **备份记录**：
   - 每个备份包含修改摘要和时间戳
   - 支持查看历史备份内容
   - 支持选择性恢复特定文件
